## Firebase Core initialization fix

Before this change, neither main.dart nor AppDelegate explicitly initialized
Firebase. The installed native Core plugin can auto-configure a default app at
plugin registration when it finds the plist (verified in its
`FLTFirebaseCorePlugin.swift:31` singleton). Consequently the absent Dart call
does not prove native Firebase was never configured; native runtime was not
observed. The app lacked explicit Dart readiness coordination.
`lib/core/notifications/firebase_bootstrap.dart` now provides one process-scoped
initializer. `main.dart` starts it after preferences initialization without
awaiting it, preserving the existing splash timing and Laravel startup.

It initializes only native iOS, the sole verified Firebase-configured platform.
It uses the bundled native options, reuses an existing default Firebase app,
coalesces concurrent callers, and caches the result. Failure returns false and
logs only a safe error code/type, so optional push setup cannot prevent login.
No permission dialog or FCM API is called by this bootstrap. Future messaging
setup must await a successful initialization result. Firebase Core is device
configuration, not Laravel authentication, and is not recreated on account
switches.

Android's actual applicationId is still `com.example.travibe`; there is no
`android/app/google-services.json` or Google Services Gradle plugin. No Android
Firebase app identity was guessed, changed or initialized. Web/macOS similarly
have no verified Firebase app options; initialization is skipped there. A future
FlutterFire CLI configuration should match existing Firebase app registrations
and generate platform options without overwriting the working iOS plist.

## Follow-up: exact SwiftPM blocker identified

On the subsequent download-stall investigation, process inspection found **two
concurrent Travibe Xcode resolvers**. One was an orphan from the earlier timeout:
Xcode/Git had spawned separate process groups, so the old process-group-only
cleanup did not stop every descendant. The other belonged to the IDE launch.
Their Firebase clone/update children had been running against the same project
repository location for over ten minutes. Both stalled resolver trees were
stopped by descendant PID, without deleting caches or application files. Future
bounded attempts explicitly terminate descendants even across process groups.

The existing shared SwiftPM repository cache contained the required Firebase
13.1.1 commit and a complete 237MB Git pack. `git fsck --connectivity-only
--no-dangling` and `git cat-file -e 13.1.1:Package.swift` passed. A single
resolution using this cache and `-skipPackageUpdates` proceeded beyond fetching
and exited with **74**, exposing an actual native version incompatibility:

```text
firebase_messaging-17.0.1 -> firebase-ios-sdk 13.1.1
google_sign_in_ios-6.3.1 -> GoogleSignIn-iOS 9.0.0..<10.0.0

Firebase 13.1.1 requires app-check 12.0.0..<13.0.0.
GoogleSignIn 9.2.0 requires app-check 11.0.0..<12.0.0.

Firebase 13.1.1 requires gtm-session-fetcher 4.0.0..<6.0.0.
GoogleSignIn 9.0.0/9.1.0 require gtm-session-fetcher 3.3.0..<4.0.0.
```

These ranges do not intersect. The previous audit's lack of a concrete resolver
error is superseded by this result; this is now a confirmed **dependency
conflict**, rather than an unproven network failure. The long initial fetch and
overlapping resolver processes obscured it. No direct manually added Firebase
reference exists in Runner, and removing the plugin-managed Firebase dependency
would break FlutterFire.

Checked the official current `google_sign_in_ios` **6.3.8** archive without
installing it: its Swift manifest still requires native GoogleSignIn **9.x**.
Live native repository tags include 10.0.0 and 10.1.0, but these are excluded by
the Flutter plugin's major-version range. Upgrading only to 6.3.8 therefore
cannot solve this graph. No speculative package upgrade or lockfile edit was
made. Firebase's official
[iOS release notes](https://firebase.google.com/support/release-notes/ios)
also document the Firebase 13 / Google Sign-In SwiftPM compatibility gap.
